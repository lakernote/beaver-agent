# 学习：RAG（检索增强生成）

对应源码：`internal/search/rag.go`（约 200 行，纯标准库，带测试）。

## 1. 为什么需要 RAG

模型不知道你的私有资料，上下文窗口也装不下整个知识库。RAG 的做法：**提问时先检索出最相关的几段，再把它们塞进提示词让模型据此回答。**

```text
知识库文件 ─► 切块 ─► 建索引          （离线，一次）
问题 ─► 检索 top-K 块 ─► 拼进提示词 ─► 模型回答并给出处   （在线，每次提问）
```

## 2. 本项目的最小实现

| 步骤 | 函数 | 要点 |
| --- | --- | --- |
| 切块 | `SplitText` | 按空行分段，再合并到约 800 字；不拦腰截断句子；记录起始行号用于引用 |
| 分词 | `Tokenize` | 英文按单词，中文按相邻两字（bigram），无需分词词典 |
| 建索引 | `NewIndex` | 统计每块词频、每个词出现在多少块里（文档频率） |
| 检索 | `Index.Search` | BM25 打分，取分最高的 K 块 |

### BM25 一分钟

`得分 = Σ(每个查询词)  IDF × 词频饱和项`

- **IDF**：越稀有的词越有区分度（“的”几乎没用，“cron”很有用）。
- **词频饱和**：出现 10 次不比出现 3 次相关 3 倍，由 `k1` 控制。
- **长度归一**：长块自带更多词，要打折，由 `b` 控制。

## 3. 关键取舍（面试/学习重点）

- **块大小**：太大 → 相关片段被稀释；太小 → 丢失上下文。800 字是常见起点，应按自己的资料调。
- **关键词 vs 语义检索**：BM25 对“专有名词、命令、报错信息”很强，对“换种说法问同一件事”很弱；向量检索相反。生产里常两者结合（混合检索）。
- **出处必须保留**：`Chunk.Source` / `Line` 让回答可核对，这是减少幻觉最便宜的办法。
- **检索不到要诚实**：`Search` 无命中时返回空，工具应告诉模型“没找到”，而不是让它编。

## 4. 升级到语义检索

只需替换“打分”这一步，流程不变：

1. 对每个 `Chunk.Text` 调用 Embedding 接口（OpenAI `/v1/embeddings`，或本地 Ollama `/api/embeddings`），得到向量，存到 `Chunk` 里（可落盘到 SQLite，避免每次重算）。
2. 对问题同样算向量。
3. 用**余弦相似度**排序：`cos(a,b) = a·b / (|a||b|)`。
4. （进阶）BM25 与向量分数各自归一化后加权，即混合检索。

## 5. 把它接成 Agent 的工具

RAG 在 Agent 里就是**一个普通的 Tool**：模型决定何时检索，工具返回最相关的片段。本项目里 `internal/search` 的真实使用者是长期记忆（[learn-memory.md](learn-memory.md)）：`memory_search` 就是“检索工具”的完整范例，可以直接对照阅读 `internal/builtin/tools/memory.go`。

如果你想接入自己的文档库，只需仿照它再写一个工具：启动时 `BuildFromDir(目录)` 建索引，工具里调用 `index.Search(query, 5)`，把 `[来源:行号] 片段` 返回给模型。

## 6. 练习

1. 运行 `go test ./internal/search -run Search -v`，读懂测试，再给 `Search` 加一个“最低分阈值”。
2. 用 `BuildFromDir("docs")` 写个小 main，搜索“定时任务”，观察命中片段。
3. 调整 `maxChunkRunes` 为 200 / 2000，看同一问题的排序如何变化。
4. 实现第 4 节的向量检索版本，并与 BM25 对比同一批问题的命中。
