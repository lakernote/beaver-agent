# Code review

审查期间只读代码，不修改文件；除非用户明确要求，否则不要顺手修复。

## 1. 取得变更
- 用户给了 Diff 或文件：直接审查，同时读取相关调用方和被调用方，不要只看孤立片段。
- 审查仓库：先用 `git status`、`git diff`（已暂存用 `--staged`，分支对比用 `git diff <基线>...HEAD`）确定范围；Diff 很大时，先用 `--stat` 找出高风险文件，逐个读取。
- 说明本次审查的范围；范围不清楚时先问用户，不要猜。

## 2. 查什么（按优先级）
1. 错误结果、崩溃、数据丢失或损坏。
2. 权限绕过、输入未校验、密钥泄露。
3. 并发与资源问题：竞态、死锁、未关闭的连接或文件、无上限增长。
4. 破坏现有调用方或持久化数据的兼容性问题。
5. 缺失的错误处理、边界条件、测试。

不报纯风格、命名、格式问题，也不报工具（linter、编译器）已能发现的问题。

## 3. 每条发现必须有
- 位置（`文件:行号`）与一句话结论。
- 触发条件：什么输入或时序下出问题。
- 影响：会发生什么。
- 证据：引用相关代码，或运行相关测试的真实结果。
- 证据不足时标为“待确认”，并写出需要核实什么，不要写成确定缺陷。

## 4. 严重程度
- **高**：数据丢失、安全问题、主流程崩溃或结果错误。
- **中**：特定条件下出错，或缺少关键测试。
- **低**：可维护性或边界情况，影响小。

## 5. 测试
新增分支要有对应测试，且断言能捕获该问题，而不只是覆盖代码行。能安全运行时就运行相关测试，引用真实结果。

## 6. 输出
先给 **结论**（一句话：可合并 / 需修改 / 有待确认问题），再按严重程度从高到低列 findings。没有发现时，说明已检查的范围和仍未覆盖的风险，不要为凑数硬找问题。
